# Native field app — contract and limits

Isolated subproject: `apps/native`.

This is a true React Native (Expo) shell for one signed-in **assigned-job / Today** read flow. It is not the public website, not the owner/admin Today page, and not a WebView wrapper.

## Session boundary

Web sessions stay on the httpOnly `tbbt_session` cookie (`src/lib/auth.ts`). Native clients cannot safely reuse that cookie transport, and must not copy passwords into the app binary.

The native contract:

1. `POST /api/native/v1/session` verifies email/password (and TOTP when enabled) on the server.
2. The server creates a normal `Session` row and returns the raw token **once**.
3. The app stores only that token in OS secure storage (`expo-secure-store`).
4. Later calls send `Authorization: Bearer <token>`. The server hashes the token and looks up `Session.tokenHash`.
5. Workspace comes from the caller's own active `Membership`. `X-TBBT-Workspace` is accepted only when that membership already exists.

The edge proxy lets `/api/native/` through without a cookie so Bearer auth can run. Missing or invalid tokens still receive 401 from the route.

`POST /api/native/v1/session` rejects bodies over 4 KB and stores password failures on `NativeSignInThrottle` (hashed email, five tries per 10-minute window). Concurrent wrong-password requests increment with a single `INSERT … ON CONFLICT`, so five simultaneous failures for a fresh email count as five. TOTP failures use the same durable `AuthChallenge.failedAttemptCount` as web sign-in. Neither counter is process memory.

## Field scope

`GET /api/native/v1/today`, `GET /api/native/v1/jobs/:jobId`, `GET /api/native/v1/time-cards`, `POST /api/native/v1/time-cards/corrections`, `POST /api/native/v1/jobs/:jobId/start`, `POST /api/native/v1/jobs/:jobId/complete`, `POST /api/native/v1/jobs/:jobId/stop-time`, `POST /api/native/v1/jobs/:jobId/start-activity`, `POST /api/native/v1/jobs/:jobId/stop-activity`, `POST /api/native/v1/jobs/:jobId/time/sync`, `POST /api/native/v1/jobs/:jobId/visit`, `POST /api/native/v1/jobs/:jobId/checklist`, `POST /api/native/v1/jobs/:jobId/checklist/sync`, `POST /api/native/v1/jobs/:jobId/pickup`, `POST /api/native/v1/jobs/:jobId/problem`, `GET/POST/PATCH/DELETE /api/native/v1/push-devices`, and the assigned-job photo routes under `/api/native/v1/jobs/:jobId/photos` use the same assignment clause as Field Home: `businessId` + `assignedMembershipId` in one query. Device-token register and revoke are membership-scoped instead: `businessId` + the caller's active `membershipId`. Time-card reads and correction requests are worker-scoped instead: `businessId` + the caller's `membershipId` on that worker's own `TimeEntry` rows.

Today is also **capped**. `listNativeAssignedJobs()` takes at most `NATIVE_TODAY_JOB_LIMIT` assigned jobs (currently 20), ordered by `scheduledAt` then `id`. If more assigned jobs exist, the payload sets `truncated: true` and `truncatedNotice`. The extra assigned rows are not returned. Cross-tenant and other workers' jobs are never part of that page. Job detail by id is unchanged: one assigned job, or 404.

Returned job data is operational only: status, schedule, customer name/phone, address, access lines, approved-scope descriptions/quantities, whether **Start job** / **Complete job** / **Stop job time** / **Start travel** / **Stop travel** / **Start material pickup** / **Stop material pickup** are available, the caller's running or recorded JOB / TRAVEL / MATERIAL_PICKUP time on that job, that job's purchase-list pickup items (needed quantity, location, ready flag, and any worker-recorded picked-up quantity or exception — not vendor prices), assigned-job photos (captions, stage, and short-lived private preview URLs), crew checklist items when the Job already has them (any trade), OWNER-recorded Job milestones on the assigned Job screen (Open/Completed labels and recorded dates; read-only — completion stays the existing OWNER action), recorded field problem reports (type, description, Open/Resolved, and reported time — capped), and — on Cleaning jobs only — the recorded visit outcome. Milestone reads reuse the assigned-job authorize (`businessId` + `assignedMembershipId`) then list `JobMilestone` rows for that job and business only, capped at `NATIVE_JOB_MILESTONE_LIMIT`. Problem-report reads use the same assigned-job authorize then list `JobProblemReport` rows for that job and business only, capped at `NATIVE_JOB_PROBLEM_REPORT_LIMIT`. The Job screen reloads those lists when the assigned job is opened. Native Today also returns one read-only **Open assigned stops in maps** handoff: complete same-business addresses on the caller's assigned jobs for the current business day (`listNativeAssignedDayJobs`, appointment order), plus the stops excluded from that link. That day query is separate from the 20-job Today list so older assigned rows cannot starve today's maps stops. The maps URL reuses the owner day-route handoff and stops at 11 complete addresses. Address text on Today and job detail uses `nativeAssignedJobDisplayAddress`: foreign or missing properties stay hidden; incomplete street-only rows can still be shown and are not maps-eligible. A literal `|` in an address part is stripped before waypoints are joined. Job detail still uses the existing `directionsHref` for one assigned job, through `nativeAssignedJobDirectionsHref`: same-business rows keep a per-job maps URL even from street-only text; a job incorrectly linked to another business's property does not return that street on `address` or `directionsHref`. Time cards return only the caller's own recent recorded entries plus any correction-request status. It does **not** return invoices, estimate totals, unit prices, wages, customer emails, portal tokens, other members' jobs, or owner Today / management records.

MEMBER access stays field-scoped. OWNER/ADMIN using this API also only see, start, complete, stop job time, start/stop travel and material pickup, record picked-up quantities or exceptions, record and sync checklist progress, record visit outcomes, and record field problem reports on jobs assigned to themselves, and request corrections on their own recorded time. An OWNER who is not assigned still sees recorded pickup on the existing purchase-list / owner pickup feed and recorded problem reports on the existing Work Order Field Reports list.

Assigned-worker writes:

- **Start job.** `POST /api/native/v1/jobs/:jobId/start` locks the assigned Job, rechecks `businessId` and `assignedMembershipId` on that locked row (same assignment-change protection as native Complete job), then reuses `startJobWithRunningTimeSafetyInTransaction` — `evaluateStartJob` plus an idempotent RUNNING JOB clock-in. Already-started jobs with running JOB time are a successful no-op. A completed job, a job that is not assigned to the caller, or a job in another business is refused. Unconfirmed appointments are refused with the same Field start gate. If the assignment changes after the authorize read, the former worker is refused and no Job, time, or start-event write happens. If the timesheet week is approved, the transaction rolls back and the Job stays `SCHEDULED` with no new time.
- **Complete job.** `POST /api/native/v1/jobs/:jobId/complete` locks the assigned Job, rechecks `businessId`, `assignedMembershipId`, and status on that locked row (same assignment-change protection as Cleaning `VISIT_COMPLETED`), then reuses `completeJobWithRunningTimeSafetyInTransaction`. It does not send an invoice. Already-completed jobs are a successful no-op. A job that is not `IN_PROGRESS`, not assigned to the caller, or in another business is refused. If the assignment changes after the authorize read, the former worker is refused and no Job, time, or completion-event write happens. If approved timesheet time is still running, the transaction rolls back and the Job stays `IN_PROGRESS`.
- **Stop job time.** `POST /api/native/v1/jobs/:jobId/stop-time` locks the assigned Job, rechecks `businessId` and `assignedMembershipId` on that locked row (same assignment-change protection as native Start/Complete), then reuses `stopRunningAssignedJobTimeInTransaction`. It closes only the caller's RUNNING JOB time on that job and does **not** change `Job.status` or send an invoice. Already-stopped jobs are a successful no-op. A job that is not assigned to the caller or is in another business is refused. If the assignment changes after the authorize read, the former worker is refused and no Job or time write happens. If the timesheet week is approved, the transaction rolls back and the RUNNING entry stays open. After a successful write, the app reloads the assigned job and shows the recorded time state.
- **Travel and material pickup.** `POST /api/native/v1/jobs/:jobId/start-activity` and `POST /api/native/v1/jobs/:jobId/stop-activity` accept `{ activityType: "TRAVEL" | "MATERIAL_PICKUP" }`. After the assigned-job authorize read, they lock the Job, recheck `businessId` and `assignedMembershipId` on that locked row (same assignment-change protection as native Start/Stop job time), then reuse `startAssignedActivityTimeInTransaction` / `stopAssignedActivityTimeInTransaction`. Those writes follow the canonical time-card clock-in transition (close any other running clock, then open the requested activity) and never flip `Job.status` or create JOB time. Starting travel does not start the job. Stopping travel or pickup closes only that activity for the caller on that job; RUNNING JOB time stays open. Already-running start taps and already-stopped stop taps are successful no-ops. A job that is not assigned to the caller or is in another business is refused. If the assignment changes after the authorize read, the former worker is refused and no Job or time write happens. If the timesheet week is approved — including a running clock from an approved prior week while the current week is still open — the start is refused, the transaction rolls back, and no running entry is closed. After a successful write, the app reloads the assigned job and shows the distinct travel / pickup time state.
- **Visit outcome.** `POST /api/native/v1/jobs/:jobId/visit` is Cleaning-only. After the assigned-job authorize read, it reuses `recordAssignedVisitOutcome`: that operation locks the Job, rechecks `assignedMembershipId` and status, then writes `VISIT_COMPLETED` or `RE_CLEAN_REQUESTED`. `VISIT_COMPLETED` completes the existing Job in the same transaction and reuses the running-time safeguard. It does not create a later job, send a customer message, or invent a quality stamp. A Handyman job, a job that is not assigned to the caller, or a job in another business is refused. If the assignment changes after the authorize read, the former worker is refused and no visit or Job write happens. If approved timesheet time is still running, the transaction rolls back and the visit stays unrecorded. Duplicate taps of the same outcome succeed and leave one visit row. After a successful write, the app reloads the assigned job and shows the recorded outcome.
- **Crew checklist.** Every native checklist tap is local until **Sync checklist**. The Job screen does not send `POST /api/native/v1/jobs/:jobId/checklist` from a tap; it stores only changed items (with their base values) plus a fingerprint of the full expected state, shows **Unsynced** / **Saved on this phone** after that write succeeds, and sends `POST /api/native/v1/jobs/:jobId/checklist/sync` only when the worker taps **Sync checklist**. The existing live item route still reuses `setAssignedChecklistItem` for callers that post one item. Sync is trade-neutral when the Job already has checklist items: after the assigned-job authorize read it locks the Job, rechecks `assignedMembershipId`, re-reads `JobCrewVisit.checklistJson`, recomputes that fingerprint, and refuses a stale or reassigned draft, and also refuses a completed, canceled, or already-outcomed draft, instead of overwriting newer or finished work. A replay of a draft that already matches the locked row succeeds without writing. OWNER and MEMBER can both record progress only when the job is assigned to them. A job with no checklist items, a job that is not assigned to the caller, or a job in another business is refused. Sync does not complete the job, write time, or send a message. After a successful sync, the app reloads the assigned job and clears the local draft. A stale 409 reloads the assigned job so the worker sees the newer checklist. Complete job and visit-outcome taps require sync or discard first when a local draft is unsynced. Local drafts stay on the phone across a failed session restore unless the server returns 401/403 or the worker signs out or switches accounts. If a draft cannot fit more changes, the app says **Sync before more changes** and keeps the taps already saved.
- **Pickup items.** `POST /api/native/v1/jobs/:jobId/pickup` accepts `{ itemId, quantityPickedUp?, pickupException?, pickupExceptionNote? }`. After the assigned-job authorize read, it reuses `recordAssignedJobPickup`: that operation locks the Job, rechecks `assignedMembershipId`, locks the existing `MaterialPurchaseListItem` for this job, then writes the picked-up quantity and/or exception. OWNER and MEMBER can both record pickup only when the job is assigned to them. It does not purchase the item, change `quantityPurchased` / actual cost / status, append supplier price history, create an expense, or start MATERIAL_PICKUP time. A job that is not assigned to the caller, an item that is not a pickup row on that job, or a job in another business is refused. If the assignment changes after the authorize read, the former worker is refused and no purchase-list write happens. Duplicate taps of the same quantity and exception succeed and leave one recorded state. After a successful write, the app reloads the assigned job and shows the recorded pickup. The owner purchase-list board and owner pickup feed show the same recorded quantity or exception.
- **Job photos.** The assigned worker captures or chooses a photo, reviews it (stage + optional caption), then the app authorizes a private R2 upload, PUTs the bytes to the signed URL, and finalizes a `JobPhoto`. Image bytes never enter the Next.js route. Another worker in the same business, or another business, cannot authorize, finalize, or read the photo. Uploads are capped at `NATIVE_JOB_PHOTO_LIMIT` photos per job (currently 12) and `FIELD_JOB_PHOTO_MAX_BYTES` (12 MB). Finalize locks the assigned Job (same `lockTenantOwnedJob` as Start/Complete), rechecks `assignedMembershipId`, and recounts photos before persist: simultaneous finalizes cannot create more than 12 rows, and a reassignment after the authorize read refuses the former worker with no `JobPhoto`. A refused persist discards only the matching private `field-job-photo` READY asset for that job (business, job, category, and purpose) and uncharges storage. An asset already attached to a `JobPhoto`, or a READY asset from another job or category, is left untouched. Successful finalize and a duplicate finalize of the same asset keep the READY photo. Oversized files, unsupported types, missing storage, and the count cap return those errors to the Job screen.
- **Problem report.** `POST /api/native/v1/jobs/:jobId/problem` accepts `{ kind, description }`. After the assigned-job authorize read, it reuses `reportAssignedJobProblem`: that operation locks the Job, rechecks `businessId`, `assignedMembershipId`, the exact active Membership, and Job status, then writes an OPEN `JobProblemReport`. OWNER and MEMBER can both record a report only when the job is assigned to them. It does not complete, cancel, or reschedule the job, write time, or send a customer message. A job that is not assigned to the caller or is in another business is refused. If the assignment changes after the authorize read, the former worker is refused and no report write happens. Duplicate taps of the same type and description succeed and leave one OPEN report. After a successful write, the app reloads the assigned job and shows the recorded report. The existing owner Work Order Field Reports list shows the same row.
- **Offline start/stop.** Start job, Stop job time, Start/Stop travel, and Start/Stop material pickup stay live when the phone can reach the server. When the network drops, or when a local draft is already waiting, the Job screen records only a start or stop intent on the phone and shows **Unsynced time · Saved on this phone**. That overlay is never approved server time and never changes `Job.status` or `TimeEntry` until the worker taps **Sync time**. Sync sends `POST /api/native/v1/jobs/:jobId/time/sync` with a fingerprint of the expected clock state plus the intended tap instants, then reuses `startJobWithRunningTimeSafetyInTransaction` / `stopRunningAssignedJobTimeInTransaction` / `startAssignedActivityTimeInTransaction` / `stopAssignedActivityTimeInTransaction`. After the assigned-job authorize read it locks the Job, rechecks `assignedMembershipId`, and refuses a stale or reassigned draft, an approved timesheet week, an overlapping clock, a duplicate tap, a start earlier than time already running, out-of-order intended instants, a tap older than 24 hours, and a stop/close longer than 24 hours. Older or longer edits go through the existing time-correction request. A replay of a draft that already matches the locked clock succeeds as already synced without writing a second entry. Complete job and visit-outcome taps require sync or discard first when a local time draft is unsynced. Local drafts stay scoped to the signed-in worker (`businessId` + `membershipId`) and are cleared on sign-out or account switch. If a draft cannot fit more changes, the app says **Sync before more changes** and keeps the taps already saved.
- **Job alerts (optional).** `GET/POST/PATCH/DELETE /api/native/v1/push-devices` register, update opt-in, and revoke a device token for the caller's active membership only. Default is off. An OWNER/ADMIN assigning a Handyman job, or materially rescheduling one already assigned to that worker, may send an informational native alert through the fake/disconnected adapter. The payload is job id + generic copy. It never includes a customer address or access code, and it never starts time or accepts an appointment. Opening the notice only loads the existing assigned-job screen. Deactivating the membership revokes its tokens. Development uses `TBBT_NATIVE_PUSH_ADAPTER=fake`; Vercel production cannot enable that adapter and never talks to Expo, FCM, or APNs.
- **Time-card correction.** `GET /api/native/v1/time-cards` lists the caller's own recent stopped time. Entry `jobLabel` prefers the customer name, then a same-business display address (`nativeAssignedJobLabel`); a job incorrectly linked to another business's property does not return that street. `POST /api/native/v1/time-cards/corrections` accepts `{ timeEntryId, reason, proposedStartDate, proposedStartTime, proposedEndDate, proposedEndTime }` and reuses `requestTimeCorrection`. Proposed end cannot be later than now plus a 5-minute slack, duration cannot exceed 24 hours, and the proposed start cannot be more than 90 days before now and the original start. The original `TimeEntry` stays until an OWNER accepts or declines on the existing Time Cards surface. Native does not expose accept/decline, `correctTimeEntry`, week approval, or payroll. Another worker in the same business, or another business, cannot request on that entry. An approved week is refused with the same field-home gate. Active membership is re-checked inside the write transaction. After a successful request, the app reloads time cards and shows the recorded PENDING / ACCEPTED / DECLINED status.

After Start job, Complete job, Stop job time, Start/Stop travel, Start/Stop material pickup, an explicit time-card sync, a pickup-item record, a visit outcome, a problem report, or an explicit checklist sync, the app reloads the assigned job and shows the resulting status, running or recorded JOB / travel / pickup time, recorded pickup items, recorded outcome, recorded field reports, and checklist progress. After a time-correction request, the app reloads time cards and shows the recorded request status. Local checklist and time-card drafts stay on the device until the worker syncs or discards them. The app does not background-write checklist or time-card draft changes.

If the network drops, write helpers return an error instead of leaving the Job screen stuck on Starting… / Completing…. Today, Time cards, and the Job screen keep an explicit **Retry** / **Reload** (and pull-to-refresh on Job). Reload and pull-to-refresh ignore stale responses so an older refresh cannot overwrite a newer Start/Stop/Complete reload, and Job/Time-card actions stay disabled while a refresh is in flight. A 404 (`That job is not available.`) or a 403 whose message is that job/workspace is not available clears the stale assigned job and hides Start / clock / Complete actions. A 403 for a lapsed SaaS subscription or a time entry that is not the worker's own keeps the job or Time cards payload visible and shows the error. A mid-session 401 (or a 403 workspace-unavailable message) clears the token and returns to sign-in instead of retrying forever.

## What this slice does not do

- A standalone time clock, owner/admin checklist editor, a second Job-detail maps URL, owner accept/decline of time corrections, or worker milestone completion
- Route optimization, geocoding, or ETA claims on the assigned-stops maps link
- Owner/admin Today, Reports, invoices, payroll edits, or management console
- App Store / Play distribution, device attestation, or compiled iOS/Android binaries
- Real Expo, FCM, or APNs delivery — development uses the fake adapter only
- Website UI changes
- Cookie fallback on native routes
- Storing passwords or website credentials in the app
